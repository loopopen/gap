# Upgrading to v1.0.0

This note covers an application that already uses v1.0.0-beta.7.

## Modules

Upgrade the core module and every bundled broker or storage module in the same change:

```bash
go get github.com/loopopen/gap@v1.0.0
go get github.com/loopopen/gap/broker/xrabbitmq@v1.0.0
go get github.com/loopopen/gap/storage/xgorm@v1.0.0
```

Replace the module paths with the integrations the application imports. A core module and a broker or storage module from different releases are not supported.

Run `gapc` again after the upgrade and commit the generated handlers.

## Database

No migration. The `CREATE TABLE` statements shipped in v1.0.0 are the same schema as v1.0.0-beta.7. Opening storage creates a missing table and does not change one that already exists.

After v1.0.0, a storage module that changes its tables ships the migration, and the application runs it when upgrading that module.

## Worker ID

Remove `gap.WorkerID` from `gap.New`. Call `gap.SetWorkerID` when the process should use a fixed Snowflake node:

```go
if err := gap.SetWorkerID(workerID); err != nil {
    return err
}
```

A later successful call replaces the node. A rejected call leaves the current node in place. If `SetWorkerID` is never called, the first `gap.New` chooses the node.

## GORM

Remove `xgorm.DB`. Open storage with `xgorm.DSN` and keep the application's `*gorm.DB` for `DoInTx`:

```go
gap.New(
    gap.DoInTx(db),
    xgorm.UseGorm(xgorm.DSN(dsn, mysql.Open)),
    xrabbitmq.UseRabbitMQ(xrabbitmq.URL(url)),
)
```

GAP's pool and the application's pool are separate connections to the same database.

## Consumer group

`gap.HandleTopic`, and any other handler registered without a group, now uses `gap.DefaultGroup`, whose default is `default`. Received rows stored with an empty group are not claimed by that handler. Handlers that pass a group, including groups generated by `gapc`, keep that group. Set `gap.DefaultGroup` before startup when the omitted group should be a different name.
